对，你抓到了核心。**`C` 是固定长度（H 维）的向量，源句越长，要压进去的信息越多，必然「溢出」——不是物理溢出，是信息损失。**

## 具体说「溢出」

`C = h_T` 是一个 `H` 维向量（比如 H=128）。

- 源句 3 个词：「我爱你」——3 个词的信息压进 128 维，够用。
- 源句 30 个词——30 个词的语义压进 128 维，**不够装**。
- 源句 100 个词——**严重不够**，信息大量丢失。

**`H` 是固定的，源句长度是变化的。** 长度超过 `H` 能承载的信息量，就「溢出」——**不是报错，是信息被挤掉、丢失**。

## 一个类比

把 `C` 想象成「**一张固定大小的便签**」：

- 源句短：便签写得下，信息完整。
- 源句长：便签写不下，只能**摘要**——细节丢了。
- decoder 只看这张便签，**看不到被丢掉的细节**。

**「溢出」= 便签写不下 = 信息被压缩/丢弃。**

## 但「溢出」不是唯一问题

即使源句不长，`C` 还有另一个问题：**decoder 每一步都看同一个 `C`，不能「聚焦」**。

比如翻译「我 爱 你」→ "I love you"：

- 生成 "I" 时，最好**重点看「我」**。
- 生成 "love" 时，最好**重点看「爱」**。
- 生成 "you" 时，最好**重点看「你」**。

但 `C` 是**整个源句的压缩**——decoder 每一步看到的都是「混合了三个词的语义」。**它没法「这一步只看『我』」。**

**Peeky 也是同样问题**——它每步拼的是**同一个 `C`**，只是拼得更频繁，但内容不变。

## 所以 attention 解决两件事

1. **信息溢出**：不再压成一个 `C`，而是**保留 encoder 所有 `h_t`**（每个词一个），decoder 需要时去取。
2. **不能聚焦**：decoder 每一步**动态加权**看所有 `h_t`，自己决定「这一步该重点看哪个词」。

```
普通/Peeky:  decoder 每步 → 看同一个 C（压缩的、固定的）
Attention:   decoder 每步 → 看所有 h_t，加权求和（不压缩、可聚焦）
```

## 一句话

> **对，`C` 是固定长度的向量，源句越长，信息越「溢出」（被压缩/丢失）。** 而且 `C` 是「整个源句的混合」，decoder 每一步看同一个 `C`，**不能聚焦到源句的某个部分**。**Attention 解决这两个问题：保留 encoder 所有 `h_t`（不压缩），decoder 每步动态加权看它们（可聚焦）。**

## 顺带：为什么 attention 不「溢出」

因为 attention **不把源句压成一个向量**。它保留 `h_1, h_2, ..., h_S`（每个词一个 `H` 维向量），decoder 需要时**直接访问这些向量**。

- 源句 3 个词：3 个 `h_t`。
- 源句 100 个词：100 个 `h_t`。

**信息量随源句长度增长，不固定。** decoder 每步从这 100 个里「挑」需要的——**没有压缩，没有溢出**。

**代价**：计算量随源句长度增长（要算每步和每个 `h_t` 的权重）。但这是值得的——**用计算换信息完整**。

## 再顺带：attention 的「聚焦」怎么实现

decoder 每步算一个**权重分布**：

```
生成 "I" 时:   权重 = [0.8, 0.1, 0.1]     ← 重点看「我」
生成 "love" 时: 权重 = [0.1, 0.8, 0.1]     ← 重点看「爱」
生成 "you" 时:  权重 = [0.1, 0.1, 0.8]     ← 重点看「你」
```

然后**加权求和**：

```
context_t = 0.8 * h_我 + 0.1 * h_爱 + 0.1 * h_你    ← 生成 "I" 时的 context
```

**这个 `context_t` 是「动态的 `C`」——每步不同，聚焦不同部分。** 这就是 attention 的核心。
